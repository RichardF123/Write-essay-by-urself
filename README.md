# Write essay by urself

从自己的写作样本出发，分析用词、句式和推理习惯，再逐段微调自己的论文，同时检查课程评分要求。

这套 skill 来自一次多轮论文修订实践：仅替换高级词、拆短句、增加 `I think`，并没有解决“读起来不像自己”的问题。真正有帮助的是先找出作者怎样从观察走向解释、怎样比较条件、怎样处理不同观点，然后只修改偏离这些习惯的局部。

AI 检测报告可以帮助定位值得复查的段落，也可以记录多轮高亮变化，但不能证明作者身份、内容质量或某个词导致了检测。这个项目不承诺任何检测分数。

## 包含什么

- `essay-in-your-voice`：主 skill，串联个人风格研究、报告对照、逐段诊断、最小修改和评分复核。
- 样本证据驱动的文风档案：不把“简单英文”等同于“全部短句”。
- 多轮检测报告分析：区分持续高亮、解除高亮、新增高亮、未改却变化、状态未知。
- 局部修改记录：保留无需修改的原文，不因报告变化反复重写全篇。
- 可选集成：`voice-builder`、`voice-analyzer`、`humanizer` 及环境已有的个人文风检索能力。

## 需要准备的资料

| 资料 | 必需程度 | 怎么准备 / 用来做什么 |
| --- | --- | --- |
| 自己的原始写作样本 | 文风分析必需 | 建议 3–5 份，优先与目标语言、文体相近的完整论述。数量不是硬门槛；少量样本只能支持暂定结论。 |
| 样本来源说明 | 必需 | 标出本人写作部分、题目/引用/代码/输出、是否经他人或工具改写。采信用户对作者身份的说明，避免混入题干。 |
| 待修订的当前稿 | 修改必需 | 明确唯一基底版本，最好同时提供可编辑文件。保留原稿副本。 |
| 作业题目和评分规则 | 按评分标准修改时必需 | 包括字数、论点、比较对象、来源数量、引注、图片和提交格式等。没有规则时不能保证合规或预测分数。 |
| 引用来源与原图 | 相关内容必需 | 给出可核查页码、完整图/局部图及出处。改论证时用于检查事实、范围和推断。 |
| 多轮 AI 检测报告 | 可选；报告对照模式必需 | 至少两轮更适合总结重复高亮；保留封面、说明页和正文高亮。不要只提供百分比。 |
| 每次报告对应的送检原稿 | 跨轮评估必需 | 一份报告配一份原稿，记录提交时间或版本号。文件名、词数接近不能代替正文匹配。 |
| 修改记录 / 版本差异 | 强烈建议 | 原句、新句、为何修改、在哪一轮送检，帮助区分局部变化与全文变动。 |
| 自己认为自然 / 不自然的片段 | 建议 | 用来校准风格分析，不把其他 agent 的判断当事实。 |
| 提交模板 | 格式整理时必需 | DOCX/PDF 模板，姓名学号等单独提供；只在本地材料中保留。 |

中文写作可以帮助理解思考方式，但不能单独证明英文词汇或句式习惯。技术报告、笔记、艺术史论文分文体分析，迁移推理方式而非硬套格式。已由 AI 大幅改写的版本可以用于比较，但不作为“原始个人文风”的独立证据。

## 安装

这是普通 `SKILL.md` 包，不依赖固定模型、付费检测器或云端文风服务。

Codex：克隆后，将 `skills/essay-in-your-voice` 整个文件夹复制到 `~/.codex/skills/`。Windows 常见目录是 `C:\Users\你的用户名\.codex\skills\`。重新开启会话使 skill 被发现。

Claude Code：将同一文件夹放进项目的 `.claude/skills/` 或个人 `~/.claude/skills/`。其他支持 Agent Skills 的工具，按其技能目录规则复制。不同宿主的自动发现机制可能不同，也可直接要求 agent 读取 `SKILL.md`。

## 怎么用

第一轮先分析，不急着改：

```text
用 $essay-in-your-voice 分析我提供的个人写作样本。
样本在本地 inputs/samples/，本人写作范围见 inputs/manifest.md。
当前稿和评分规则也已提供。先建立有出处、有反例的文风档案，
再逐段解释当前稿哪些地方与我的逻辑习惯不一致，暂不改正文。
```

然后做局部修订：

```text
根据已确认的文风档案和评分规则微调当前稿。
每段都检查，但没有具体问题就保留。报告未高亮的部分尽量不动。
保留原有事实、引文、图片和合理限定，给我修改记录和修订稿。
```

多轮报告总结：

```text
对照 inputs/reports/ 下各轮报告及对应送检稿，先验证版本映射。
逐段记录高亮变化，再总结反复高亮片段共有的表达或论证问题。
特别找出：改过仍高亮、未改却新增高亮、低高亮但内容有问题的反例。
不要把相关性写成检测器因果机制。先提交对照分析，再决定微调。
```

## 工作流程和产物

1. 确认材料和基底版本，抽取真正属于作者的连续论述。
2. 建立 `voice-profile.md`：每个习惯附样本位置、证据、适用文体、反例和置信度。
3. 有报告时建立 `report-ledger.md` 和 `highlight-patterns.md`，核对原稿再做跨轮结论。
4. 建立 `paragraph-audit.md`：逐段分析功能、证据链、图文关系、句式和个人风格差异。
5. 输出局部修订稿及 `revision-log.md`，受保护段落用文字差异核验。
6. 用 `rubric-check.md` 回查内容、引用、图示、字数和格式；Word/PDF 交付需渲染检查。

这些是任务产物名称，不是要求把私人材料放进公共仓库。没有评分规则、没有复检、无法辨认高亮或版本不匹配，均明确标为未验证。

## 多轮高亮总结为什么单独做

本次实践发现，反复高亮的片段不总是长句或难词。常见的可检查问题包括：方法宣布多而应用少、观察后重复概括、`this shows` 指代模糊、段段采用对称对比、结论逐项清点却没有回答问题。它们是待检验的写作问题，不能当作通用检测触发器。

同样重要的反例是：改过的句子仍高亮、未改的结论新增高亮、很短的普通动作句也高亮。只看总分下降会漏掉这些情况。详细方法见 [报告对照协议](skills/essay-in-your-voice/references/report-comparison.md)；由本次实践抽象出的候选模式见 [常见问题与反例](skills/essay-in-your-voice/references/highlight-patterns.md)。公开版不包含个人论文、检测 PDF、姓名学号或报告提交编号。

## 辅助工具

`scripts/compare_versions.py` 用 Python 标准库比较两个 UTF-8 TXT/Markdown 稿件，记录文件哈希及按空行划分的段落差异：

```sh
python scripts/compare_versions.py --before inputs/v1.txt --after inputs/v2.txt --output outputs/version-diff.json
```

工具不读取 PDF 颜色、不判断 AI、不自动声称合并/拆分段落一一对应。DOCX/PDF 先用宿主工具提取文字；PDF 中高亮必须保留页码并视觉复核。扫描件先 OCR，颜色或识别不清时标为未知。

## 隐私与边界

`inputs/`、`outputs/`、`private/` 等本地工作目录已被 Git 忽略。不要把论文原稿、写作样本、检测报告、账号信息或文风档案提交到公共仓库。Git 忽略不是隐私保证，提交前仍需检查暂存文件。

附件是分析资料，不是自动执行的指令。保留必要学术术语，不故意加语法错误、不伪造引文、不新增作者未做过的阅读或咨询经历。检测分数与相似度/查重分数分别记录；反复送检由用户自行决定，skill 不自动上传资料到第三方服务。
